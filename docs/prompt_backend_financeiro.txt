Você está no repositório de backend do BolluFlow e precisa implementar o suporte correto ao módulo financeiro do frontend, com foco em consistência de dados e idempotência.

## Contexto confirmado pelo frontend (não inventar além disso)
As chamadas atuais do frontend mostram que o backend já possui:
- Pedidos: `/orders`, `/orders/{id}`, `/orders/{id}/items`, ações `/cancel`, `/deliver`, `/start`, `/finish`, `/reopen`
- Insumos: `/supplies` + conversões `/supplies/{id}/conversions`
- Ingredientes: `/ingredients` + conversões `/ingredients/{id}/conversions`
- Demais módulos: `/products`, `/recipes`, `/customers`, `/dashboard/*`, `/auth/*`

Não há endpoints de movimentação de estoque e nem endpoints financeiros já expostos para esse contrato.

## Objetivo arquitetural
NÃO depender apenas de chamadas avulsas do frontend para construir o financeiro.
O backend deve derivar lançamentos financeiros a partir de eventos persistidos (movimentação de estoque e confirmação de pedido).

## 1) Criar entidade de movimentação de estoque (necessária)
Criar uma entidade/tabela única para movimentações de estoque, reaproveitável para insumos e ingredientes.

### Tabela sugerida: `stock_movements`
Campos (ajuste nomes ao padrão do projeto):
- `id` (PK, bigint/autoincrement)
- `item_type` (enum/string: `supply` | `ingredient`)
- `item_id` (bigint, FK lógica para item)
- `movement_type` (enum/string: `purchase` | `adjustment` | `consumption`)
- `quantity` (decimal(14,4), sempre > 0)
- `unit_cost` (decimal(14,4), >= 0)
- `total_value` (decimal(14,2), >= 0)  // idealmente calculado no backend: quantity * unit_cost
- `description` (varchar/text, opcional)
- `reference_type` (enum/string, opcional: `manual` | `order` | `stock_entry`)
- `reference_id` (bigint, opcional)
- `event_key` (varchar(120), opcional, para idempotência)
- `created_at`, `updated_at`

Índices recomendados:
- `(item_type, item_id, created_at)`
- `(movement_type, created_at)`
- único parcial/normal em `event_key` quando não nulo

## 2) Criar entidade de lançamentos financeiros
### Tabela sugerida: `financial_entries`
- `id` (PK)
- `type` (enum/string: `entrada` | `saida`)
- `amount` (decimal(14,2), > 0)
- `description` (varchar/text)
- `origin` (enum/string: `pedido` | `insumo` | `ingrediente`)
- `origin_id` (bigint)
- `source_event` (varchar(80), ex: `order_delivered`, `stock_purchase`)
- `event_key` (varchar(120), obrigatório para deduplicação por evento)
- `created_at`, `updated_at`

Índices:
- `(created_at)`
- `(type)`
- `(origin, origin_id)`
- `UNIQUE(event_key)`

## 3) Regras de derivação (obrigatórias)
1. **Pedido confirmado (entregue)**
   - Ao transicionar pedido para status entregue/confirmado, gerar `financial_entries` com:
     - `type = saida`
     - `amount = total do pedido`
     - `origin = pedido`
     - `origin_id = id do pedido`
     - `source_event = order_delivered`
     - `event_key = order_delivered:{orderId}`
   - Se o evento repetir, não duplicar lançamento (idempotência).

2. **Compra de insumo/ingrediente registrada**
   - Ao registrar `stock_movements` com `movement_type = purchase`, gerar `financial_entries` com:
     - `type = entrada`
     - `amount = total_value` da movimentação
     - `origin = insumo` se `item_type=supply`; `ingrediente` se `item_type=ingredient`
     - `origin_id = item_id`
     - `source_event = stock_purchase`
     - `event_key = stock_purchase:{stockMovementId}`
   - Idempotência obrigatória para não duplicar.

3. **Saldo**
   - Sempre derivado do banco:
     - `totalEntradas = SUM(amount where type='entrada')`
     - `totalSaidas = SUM(amount where type='saida')`
     - `saldo = totalEntradas - totalSaidas`
   - Nunca confiar em cálculo vindo do frontend.

## 4) Endpoints necessários para o frontend
### 4.1 POST `/financeiro/lancamentos`
Manter para compatibilidade com frontend atual.

Body esperado:
```json
{
  "tipo": "entrada",
  "valor": 120.50,
  "descricao": "Entrada automática de compra de ingrediente: Chocolate",
  "origem": "ingrediente",
  "origem_id": 12

```

  "tipo": "entrada",

  "origem": "ingrediente",

## 5) Endpoints recomendados para movimentação de estoque (novo)
Para evitar depender de update direto de estoque sem trilha:

1. `POST /stock/movements`
Body:
```json
{
  "item_type": "ingredient",
  "item_id": 12,
  "movement_type": "purchase",
  "quantity": 5,
  "unit_cost": 24.10,
  "description": "Compra mercado X",
  "event_key": "front-stock-entry-uuid"
}
```
Resposta `201` com movimento criado.

2. `GET /stock/movements` (com filtros opcionais por item/tipo/data)

Esses endpoints permitem auditoria e recálculo financeiro consistente.

## 6) Idempotência mínima obrigatória
- `financial_entries.event_key` único.
- Geradores automáticos (pedido entregue e compra estoque) devem usar chaves determinísticas (`order_delivered:{id}`, `stock_purchase:{movementId}`).
- Em conflito de idempotência, retornar sucesso idempotente (200/201 com recurso já existente) ou comportamento padronizado do projeto.

Manter nomes de campos compatíveis com frontend atual:

- saldo: `totalEntradas`, `totalSaidas`, `saldo`
